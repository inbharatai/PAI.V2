# Android independent local file-vault foundation

The default file destination is `Context.noBackupFilesDir/local-file-vault`, not a drive or Power. `MobileVaultRepository.create` generates a fresh UUID, 32-byte random master key, salt and wrap nonce and writes the **existing** Rust `VaultHeader` format (Argon2id 256 MiB / 3 iterations / 4 lanes; existing XChaCha master-key wrap/HMAC; existing AES-GCM record format). No new cipher, dependency, password reset, mnemonic generator, recovery-word scheme or desktop key copy is introduced. A user-entered long phrase is simply a password.

`PrivateFileVaultIO` rejects path traversal, symlinks and special files; bounds each file at 16 MiB and directory listings at 100,000 entries. Repository writes bound plaintext at 4 MiB and headers at 64 KiB. New directories/files use owner-only permissions. Writes fsync a fresh same-directory temporary file, atomically rename without a non-atomic fallback, then fsync the containing directory. Parent directory creation is fsynced. The Android adapter supplies `Os.fsync`; host tests use real FileChannel fsync. There is no physical deletion operation; tombstones reuse the existing authenticated format. Interrupted temporary files are retained, never promoted or deleted automatically. A nonempty root cannot be recreated/reset. This is a single-process app-sandbox boundary, not protection from a compromised same-UID writer or a multi-process vault service.

The Local vault panel offers create/confirm-password, unlock and lock. The password is not saved in preferences/saved-instance state; input fields clear on submission/backgrounding. Byte buffers and session master keys are zeroized when consumed/closed, with best-effort cleanup of derived keys. JVM/Compose immutable strings and cipher-provider internals cannot carry a guarantee of complete memory erasure. By default Activity backgrounding revokes handles immediately and closes the file session off the main thread. Keeping the file vault open in the background is a per-process explicit opt-in; nothing persists the unwrapped file key. This lock **does not** lock or erase the existing, separate encrypted Room store.

## Historical data safety

Creation inspects existing Room links, pending writes and pending tombstones without modifying them. If any exist, the new file vault gets a durable `migration-required` binding: it may unlock but the Room/file bridge remains paused. Missing/unknown bindings after interrupted creation also pause it. Do not replace this with “just drain the old queue”: current outbox rows do not identify their source vault, and silently rebinding them could retire legacy operations against an unrelated key/UUID. New installations with no historical references use the existing Room/VaultMirror mutation path; locking leaves pending operations retained for the next unlock. This foundation does **not** redesign the Room/outbox transaction or namespace protocol.

USB selection is explicit and read-only. It is a separate legacy source; unplugging never replaces/locks the local destination. Review authenticates supported readable records and presents an import **proposal count**, not an executed or complete import. Corrupt/unparseable metadata can be skipped by the inherited listing implementation, and legacy XChaCha record payloads remain unsupported in Kotlin (the existing Rust reader supports them). Counts are not a complete migration audit. No legacy hydration, synced JSON permission, executable skill activation, remote execution or raw-key transfer is performed. Backup, counts/hashes/tombstone validation, transactional migration and rollback must precede a real import.

## Gates and limits

- Existing Argon2id needs **256 MiB plus a conservative 96 MiB estimated heap allowance**. One derivation runs at a time across local/legacy repositories. Insufficient JVM app heap is refused before allocating Argon2; no lower-cost incompatible KDF is substituted. Many ordinary Android heaps may not qualify. Existing encrypted Room storage remains usable; physical memory/latency qualification and a separately approved compatible solution for low-heap phones are release blockers.
- No persistent password retention, recovery phrase, password change, vault backup/export/restore wizard, person/replica pairing, peer sync or network transport is claimed.
- New pure JVM tests exercise fresh independent creates, restart, wrong passwords, tamper, tombstones, lock/revocation, historical-binding quarantine, missing-binding interruption, fsync/rename fault retention, paths/symlinks and size bounds with real crypto/files. `src/test/interop/LowHeapVaultAdmission.kt` is a separate `-Xmx320m` refusal probe, not a normal Gradle test that assumes the runner's heap.
- `src/test/interop/local_file_vault.rs` opens a fresh synthetic Kotlin-created vault with the **real Rust Vault::open/unlock/read_record**, reads Unicode content and checks tombstone suppression. Existing Kotlin/Rust golden crypto/envelope fixtures remain unchanged.
- Host API/Compose compilation is not an APK/Gradle/KSP/device pass. Device tests must cover Android POSIX permissions, atomic move/fsync, lifecycle races/kill, UI creation/unlock, heap limits, restart, and same-signer historical-store upgrade. No Wi-Fi, airplane-mode, general offline or physical-device success claim follows from these host tests.
