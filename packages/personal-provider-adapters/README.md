# Personal Google provider adapters (unqualified, opt-in)

Implemented product source, **not live-account qualification**. No production OAuth client, account or redirect is bundled; first state is `UNCONFIGURED`. No Hyperagent token, new account, bulk connection, real send or calendar write was used during implementation.

## Reachable app surfaces

Both existing Personal Agent screens contain **Sources / Prepared**, not another assistant identity. Local status reads do not contact Google. Configure → explicitly authorize Google → explicitly issue bounded reads. Offline preparation is allowed for an existing selected task without calling Google. Explicit exact-review confirmation is the only commit entrypoint; these native methods are not model tools.

Power uses real `reqwest` and external system-browser OAuth authorization-code **PKCE S256** with a bound `127.0.0.1` listener, random state, 180-second callback lifetime, exact redirect/path and state validation. Input is a registered **Desktop** OAuth client ID and loopback redirect (`http://127.0.0.1:<port>/oauth/callback`), plus its optional installed-app client credential when that registration requires one. The optional credential is password-field input saved only in encrypted local config; never a borrowed account token. Browser launch is not account readiness: account is bound only after code exchange, granted-scope validation and Gmail profile read. Tokens stay in a dedicated device-local vault-core encrypted record, never UI DTOs, task data, logs or peer export. Native lock-epoch checking blocks stale sessions; the current blocking worker holds the existing vault mutex over a bounded request/OAuth flow.

Android uses real `HttpsURLConnection`, AndroidKeyStore AES-GCM and Google's official **AuthorizationClient / Google-owned PendingIntent resolution**. Google does not support transplanting desktop loopback/custom-scheme OAuth to Android. The locally entered Android client ID records configuration; Google's SDK resolves the real client from the package and signing certificate registered by the owner. **No web/server client, backend, refresh-token server or guessed redirect is introduced.** Short-lived access token is profile-bound and stored only in `noBackupFilesDir/provider-local/<vaultId>.bin`, encrypted with a non-exportable per-vault AndroidKeyStore AES key, authenticated with vault binding. Device unlock and existing VaultConnection/quarantine gates apply. After 45 minutes/401, explicitly authorize again through the SDK (previous consent can be reused); no Android refresh token is requested. Lack of Play services or valid package/signer registration stays unavailable. SDK authorization is not claimed to be our desktop PKCE implementation.

Disconnect invalidates local tokens and unattempted grants even when Google revocation fails. Remote revocation is attempted and its uncertainty is displayed; user can revoke in Google Account settings. Changing account requires disconnect. Prior provider receipts/history remain locally encrypted; disconnect is not historical secure erasure.

## Supported operations and safety

- Scoped Gmail search/list (50/page, explicit page token only), message read, thread read (20 messages; **every message** must be in requested label), label listing. MIME and email text are untrusted data rendered as escaped text, never executable HTML/approval. No attachments are downloaded.
- Plain UTF-8 mail preparation, reply metadata, provider draft save and send; at most 10 exact recipients and 16 KiB body. No CC/BCC, attachments, arbitrary MIME/headers, trash/deletion/spam classification or unattended sends. Header controls/display-name injection rejected.
- Label add/remove incl. removing INBOX to archive. Exact source folder and message must be observed first. Reserved deletion/send labels rejected.
- Calendar listing, event listing, one-calendar free/busy and conflict checks; explicit RFC3339 offsets and named zone; positive ≤31-day query/event range. Errors are **unknown**, never free. No recurrence/all-day/scheduling ambiguity auto-resolution.
- Event create/update/cancel after exact review; maximum ten attendees. Notifications use `sendUpdates=all`, disclosed in review. Update uses current ETag/If-Match and cannot remove existing attendees. Cancel requires exact current event title/time/attendees and ETag, then a cancelled-status readback. Availability checks are immediate preflight, not an atomic guarantee against other calendar writers.
- Typed Rust/Kotlin review/mutation/grant/receipt contracts and shared JSON/digest/MIME golden. Grant is non-deserializable, native-only, single-operation, exact digest including account, source folder/calendar, task/owner, full content/recipients and five-minute freshness. Editing or changing any field needs a new review. No standing/background execution grant is exposed.
- Calendar insert ID derives deterministically from operation UUID. **Before** dispatch, `NEEDS_RECONCILIATION` is committed to encrypted local provider state and selected task note. Restart/retry cannot dispatch that operation again. No automatic mutating retry, even for 429/5xx/timeouts. Read-only reconciliation takes the exact observed provider ID; unknown IDs require provider search/manual inspection using the RFC Message-ID/deterministic event ID. No exactly-once claim without provider reconciliation.
- Success requires provider ID + separate GET readback of labels, exact MIME/recipients/thread/SENT or calendar ID/status/times/zone/attendees. HTTP 200 is not enough. MIME comparison is deliberately conservative: provider normalization may leave a real send **unverified**, requiring manual reconciliation, not a resend.
- Exact HTTPS endpoints only: `accounts.google.com/o/oauth2/v2/auth`, `oauth2.googleapis.com/{token,revoke}`, `gmail.googleapis.com/gmail/v1/users/me/*`, `www.googleapis.com/calendar/v3/*`. Dynamic IDs are path-encoded. Redirects disabled, 10-second connect/25-second request/read deadlines, 1 MiB responses, 64 KiB requests, no automatic pagination, bounded pages/replies/recipients. Rate limits surface as hold/no retry.

## Existing task ledger, not forked task state

No runtime/sync implementation or schema was modified. Existing `runtime::load/apply(Request::Edit)/save` and Android `PersonalAgentService.mutate` persist selected-task pending/provider-receipt **notes** under the same task ID, including operation/account/container/provider ID. Ownership, conflict/deletion/cancellation checks precede commit. Approved task-note sync remains inert. Full reviews/provider receipts remain in the device-local provider ledger; credentials/grants never enter the personal task ledger or its sync payloads. The personal task is not promoted to native `VERIFIED` by a note.

This is deliberately **not** a new TaskReceipt runtime append API or an automatic cross-device provider dispatcher. Two encrypted writes are not claimed atomic: provider uncertainty is durable first; failure of the personal note write prevents dispatch; failure after provider readback retains the local receipt for explicit reload/reconciliation. Imported provider notes cannot execute and cannot create a local grant. Runtime receipt/event promotion, receipt-note repair UI and cross-device execution ownership transfer require a separately reviewed additive runtime interface if desired. No fork of the existing board/fold was created.

## Tests and required qualification

`cargo test -p unoone-personal-provider-adapters --locked -j1 -- --test-threads=1`: actual reqwest/loopback HTTP transport fixtures are **TRANSPORT SIMULATIONS**, not a live Google account. Includes exact readback, wrong ID/429/page/folder/freshness/header injection, real encrypted vault restart and uncertain-operation rejection, Rust/Kotlin canonical fixture. `tests/live_google.rs` is a real owner-gated PKCE/profile/calendar-read/revoke smoke journey, explicitly **ignored with reason**, not passed. To run deliberately, owner sets `UNOONE_GOOGLE_CLIENT_ID`, `UNOONE_GOOGLE_REDIRECT`, `UNOONE_GOOGLE_EXPECTED_ACCOUNT` (and optional installed-app `UNOONE_GOOGLE_CLIENT_SECRET`) and invokes `cargo test -p unoone-personal-provider-adapters --test live_google -- --ignored`. It opens the system browser, requires fresh consent and reads one bounded calendar-list page; no mail/calendar write. Even a pass would not qualify mutation/device journeys.

`tools/test_android.py`: four JVM policy/golden tests. `--api`: actual Android 35 API + Compose + official downloaded SDK compilation; no dummy Google/Android classes. Does not run handset Keystore, Play-services login, provider transport or lifecycle behavior. Parent must run full Gradle/KSP/lint/APK and Tauri native IPC/packaged WebView gates. Native desktop IPC module is rustfmt-parsed, not full-Tauri built by this slice.

Owner-only live journey: supply actual platform client registrations/redirect and disposable existing account; verify explicit read-only login/cancellation/account mismatch/revocation, scoped search/thread, local draft→review→provider draft/send/readback, conflict→event create/update/cancel/readback, disconnect and expired token, lock/background/process death, dropped-response uncertainty/reconciliation without duplicate send.
